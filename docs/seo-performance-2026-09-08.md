# SEO-17: мобильная производительность и доступность

Проверено 8 сентября 2026 года на локальной production standalone-сборке. Выполнены измерения и адресные исправления шаблона. **Полевые Core Web Vitals будущего сайта ещё не проверены; LCP каталога и карточки в последних лабораторных замерах выше 2,5 секунды.**

## Методика

Lighthouse 13.4.1, мобильный профиль 412 × 823, DPR 1,75, simulated throttling: RTT 150 мс, сеть 1638,4 Кбит/с, замедление CPU ×4. Chrome запускается headless с отдельным профилем. Использованы настоящий Next.js production-сервер, FastAPI и отдельная PostgreSQL с искусственными данными Agency Beta: 101 офис, комплекс, статья и подборка. Фотографии взяты из существующих тестовых ресурсов репозитория; это не проверка финальных фотографий компании. Последние замеры выполнялись последовательно без параллельной сборки и тестов.

Локальный origin исключает реальную задержку внешнего сервера/CDN. Кеш серверных данных и оптимизированных изображений мог быть прогрет. В двух исходных замерах Lighthouse сообщил о неподходящей скорости CPU хоста; первый также пересекался с тестами. Поэтому разницу баллов нельзя приписывать только изменениям кода или выдавать за гарантированный прирост. [Методика Lighthouse](https://developer.chrome.com/docs/lighthouse/overview/).

## Что изменено

- Настройки компании повторно используются внутри одного серверного рендера через React.cache; fetch-кеш настроек остаётся 300 секунд. Публичные карточки используют 10–60 секунд, подборки — 300 секунд. Это отдельные установки/БД/процессы; общий кеш HTML для разных компаний не вводился. [Семантика React.cache](https://react.dev/reference/react/cache).
- Скорректирован sizes основной фотографии с учётом реальной ширины мобильной карточки; сохранены ранняя загрузка главного изображения и фиксированное соотношение сторон.
- Повышен контраст CTA, результатов конвертера и мелкого текста карточки комплекса. Подписи ссылок бренда и кнопки главного фото включают видимый текст.
- Добавлен H2 над результатами каталога и подборок, чтобы карточки H3 имели родительский раздел. Пустой список использует переданный язык, без русского значения по умолчанию.
- Все типы квартир и ссылки на планы комплекса доступны в исходном HTML через раскрываемый раздел. Проверены три типа и три ссылки без выполнения клиентского JavaScript.
- Удалены неиспользуемые захардкоженные отзывы, числовые обещания и бюджетные массивы из общих словарей. Рабочие данные отзывов не изменялись.

TypeScript, ESLint и production-сборка прошли. Все три проверенных типа страниц после исправлений получили Accessibility 100 и SEO 100; это не заменяет ручную проверку с экранным диктором и анализ реального контента.

## Что остаётся

1. На финальных фотографиях повторить минимум три мобильных замера каждого основного шаблона с одинаковым устройством и состоянием кеша; включить комплекс, статью и посадочную. Карточка сейчас имеет LCP около 3,3 с, каталог — 3,0 с. Не считать эти страницы прошедшими целевой LCP.
2. Разобрать объём клиентского JavaScript на реальном наполнении: для карточки Lighthouse оценил около 49 КиБ неиспользуемого JS, 11 КиБ CSS и около 210 мс потенциального выигрыша от блокирующих ресурсов. Это диагностические оценки, а не гарантированная экономия. Первыми кандидатами являются общие клиентские провайдеры и неинтерактивные блоки; менять границы Server/Client Components по профилю нагрузки, сохранив валюту, языки, формы и галерею.
3. На сервере проверить кеш оптимизатора изображений и uploads, размеры/формат оригиналов, CDN, компрессию и TTFB. Проверить получение свежих настроек после редактирования с учётом TTL до 5 минут. Не смешивать публичный кеш с CRM, авторизацией или ссылками с токенами.
4. После публикации собрать реальные LCP/INP/CLS через PageSpeed Insights/CrUX и, при необходимости, настроенную для проекта RUM-аналитику. Ориентиры на 75-м процентиле: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1. TBT из этого отчёта не является измерением INP. [Core Web Vitals](https://web.dev/articles/vitals).
