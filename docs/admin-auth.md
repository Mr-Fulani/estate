# Авторизация и роли админки

## Поток входа

1. Founder создаётся только через интерактивную CLI-команду `python -m app.cli create-founder` с уникальным `--username`.
2. `POST /api/v1/auth/login` принимает логин или email, проверяет пароль и создаёт случайную серверную сессию.
3. Браузер получает непрозрачный идентификатор сессии в `HttpOnly`, `SameSite=Lax` cookie и отдельный CSRF cookie.
4. Next.js middleware проверяет наличие сессии перед входом в `/admin`; FastAPI независимо проверяет сессию и права на каждом закрытом API-маршруте.
5. Выход отзывает серверную сессию и удаляет обе cookie.

## Роли

| Роль | Доступ |
|---|---|
| founder | Все разделы, аккаунты команды, роли и аудит |
| admin | Все рабочие разделы и аудит |
| manager | Дашборд, объекты, CRM, отзывы и категории |
| editor | Дашборд, объекты, новости и отзывы |

Удалить или отключить последнего активного founder нельзя. Сброс пароля другим администратором и отключение аккаунта отзывают все его активные сессии.

Сотрудник может самостоятельно изменить пароль в `/admin/profile`. Для этого требуется текущий пароль; новый пароль должен содержать не менее 12 символов и отличаться от текущего. После успешной смены текущая сессия сохраняется, а все остальные сессии этого аккаунта отзываются. Попытки ограничены по частоте; успешные изменения и неверный текущий пароль записываются в аудит без сохранения паролей.

## Журнал действий

`admin_audit_logs` хранит пользователя, тип действия, тип и ID объекта, безопасные метаданные, IP и время. Пароли, session token и CSRF token в аудит не записываются.

## Production

- использовать HTTPS и `AUTH_COOKIE_SECURE=true`;
- хранить секреты вне репозитория;
- ограничить `/docs` и `/redoc` на уровне reverse proxy;
- настроить ротацию/архивирование старых сессий, login attempts и audit logs;
- включить внешнее логирование и оповещения о серии неудачных входов;
- при необходимости добавить TOTP/WebAuthn как второй фактор для founder и admin.
